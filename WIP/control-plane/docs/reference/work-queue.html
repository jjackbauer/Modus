How these counts are defined

Shown counts the rows on this page after filters. Awaiting authorization counts rows with a contract or merge approval pending. Active execution counts In implementation and In review. Terminal failures counts the factory state Failed only; a failed verification on an In-review item is an attention indicator, not a terminal failure. Overview's “Blocked or failed” uses the adapter's failed_work_items definition and can differ; each count must name its source (A-05, IA-03).

Design reference — decisions and traceability

Static PR 0 mockup, not a deployed screen. Real content from the 19 November 2026 15:59 UTC capture (ux-review/captures/api/work-items.json and the work queue capture). Event counts, priorities, states and timestamps are the captured values; no work item, metric or next action is invented. The Next step column is a presentation of the adapter's legal transition, not a second source of authority. Measured at 1440×1000 and 390×844 in both themes with headless Chrome; no horizontal document overflow.

Decision in this mockupRequirementWhy it is this way
Two-row toolbar with visible labels on every fieldB-02, VG-02The former toolbar relied on placeholders and a screen-reader-only label. Labels stay visible at every width, so the control's meaning does not vanish when a value is filled.
Search first; filters and saved views on the second rowB-02A compact 1–2 row toolbar; the search field keeps the widest flexible column while filters stay one Tab away.
Narrow screens get a Filters button, not squeezed selectsB-01, B-02At ≤700px the fields collapse behind an `aria-expanded` toggle while Search stays visible and full width.
Clear filters is present and states why it is unavailableB-02No filter is applied in this capture, so the control is disabled with a reason. With any active filter it becomes enabled.
Saved views are browser-local presentation stateB-02, IA-03A saved view never widens authority. The target implementation also restores search, filters and sort through the URL; this mockup shows the control only.
Full work ID on one line, never truncatedDS-02, VG-02DS-02 forbids arbitrary truncation of decision identifiers. The implementation pairs this with `EntityIdentity` copy; the ID remains selectable in the mockup.
State and attention are separate columns with different wordsDS-03, C-04“Operationally validated” is not repeated as a second badge. “Verification failed” appears only where it differs from the authoritative state.
Counts sit next to the rows and name their definitionA-05, IA-03“Terminal failures” is explained as state Failed, distinct from the adapter's “Blocked or failed” overview count. The disclosure prevents two numbers from silently disagreeing.
Mobile uses cards, not a clipped desktop tableB-02, VG-01Cards carry the full ID, title, state, attention, last change and one next step. The desktop table remains available at wider container widths.
Table scroll is a labelled region with a visible hintB-04, VG-01Headers stay readable and the scroll region is keyboard focusable. The hint appears when the table can overflow.
Sort definition is displayed in wordsB-02“Recently updated, newest first” is visible next to the summary. The Priority view must display its declared-priority + urgency definition when implemented.
No KPI tile grid; no status chip for neutral valuesDS-03, DS-01Four counts as a summary line, not six identical cards. Neutral values (“None”) are text, not a coloured badge.
15px body, 13px metadata; 12px only in notesDS-02, VG-02Table cells and timestamps are 13px, not 10/11px. The table header is a label, not action-critical text.
