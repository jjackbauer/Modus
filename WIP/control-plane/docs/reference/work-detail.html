Design reference — decisions and traceability

Static PR 0 mockup, not a deployed screen. Real object: WORK-18b96b98, version 9, captured 19 November 2026 15:59 UTC. Head, base, digests, check evidence, actors, timestamps and policy versions come from the adapter's review event in the factory log; the requirements and scenarios come from the frozen contract. No evidence, metric or acceptance is invented. The typed-digest field and button are live in this document only to demonstrate the disabled-until-exact behavior; nothing is submitted.

Decision in this mockupRequirementWhy it is this way
One authoritative state, one derived indicator, no chipsB-05, DS-03, status glossary §1“Ready for delivery” is the state; “Waiting for merge approval” is the derived indicator. The former header's health, dispatch-active and contract-frozen chips repeated facts already owned by their panels.
Next legal action and its consequence are visible before evidenceIA-01, IA-04The operator can answer “what can I do” without scanning the whole page. The action is the only legal transition offered from this state.
Reviewed head, base, source revision, target and verdict in the decisionA-03The dialog must display the reviewed base/head and the accepted verdict. This panel is the same body the accessible dialog renders.
Four mandatory checks with full evidence digests and copyA-03, DS-02Each digest is complete, wrap-safe and copyable. Truncating a digest an operator is binding is a safety defect, not a density choice.
Binding conditions and the exact consequence, including what it does not doA-03, VG-04“Merges the head” and “does not certify acceptance / does not serve” are both stated. A merge is never presented as verification.
Full 71-character review digest plus typed confirmationA-03, C-02The value is displayed in full, then typed. The button stays disabled until the exact value matches and the adapter revalidates independently.
Stale or changed evidence cannot confirmA-03, VG-04The panel records that the adapter refuses a changed review with a typed conflict. The reference shows “Stale evidence: None” because the head matches.
Quality deep-links here; one authorization surfaceA-03, D-01The approvals inbox links to this panel instead of duplicating the object in a second, weaker confirmation. One pending merge remains one decision.
Frozen contract object with class, digest and executable scenarioA-02Contract approval already happened; the immutable object remains inspectable with the same identity the dialog displayed before freezing.
Lifecycle shows a pending authorization, not a completed oneIA-01, A-04Six completed stages and one pending stage. No merge, release or serve record is implied. Every row has an actor, duration and exact UTC time on reveal.
Evidence is grouped by the claim it supports, with an index instead of a clipped tab stripB-05, C-01Review checks, contract, lifecycle, diff/lineage/events are progressive disclosures. At ≤1100px the layout is one column; nothing scrolls sideways.
One column at narrow widths; the decision stays firstB-01, VG-01The decision panel precedes context on mobile. No horizontal document overflow at 390px; long digests wrap at safe boundaries.
Version and policy identities are secondary mono metadataDS-02, IA-04Mono is reserved for IDs, digests, paths and policy versions. Prose and status labels use the UI face at 13–15px.
Acceptance boundary is explicitplan §11, VG-04This screen never infers evaluator-owned acceptance from local checks. The authorization says exactly what it authorizes.
